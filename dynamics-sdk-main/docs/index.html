RISE Dynamics SDK

⚠️ The SDK is currently compatible with firmware versions up to 0.10.3

Introduction

The RISE Dynamics Mobile SDK encapsulates many different tasks that are required to communicate with the RISE Smartglove (SG), it allows the consumer to easily connect with the SGs via Bluetooth Low Energy (BLE) and receive structured punch data from it.

The SDK handles the following tasks:

  • Managing BLE-related operations, including scanning the environment for new SGs, pairing, connecting, reconnecting if needed, and setting up the required BLE characteristics for communication with the SG.

  • Overseeing the internal SG states at the app level to regulate the flow of incoming data.

  • Decoding raw byte data from the internal RISE SG protocol.

  • Performing computations on raw data from the Inertial Measurement Unit (IMU) and barometric sensors.

  • Storing punch data in a SQLite database.

  • Exporting punch data.

How to start?

SDK's Tech stack

  • Java 17

  • The SDK is built with Kotlin Multiplatform v2.3.21 and supports Android and iOS targets.

  • The SDK heavily relies on the usage of Kotlin Coroutines.

iOS

⚠️ The SDK uses many Kotlin-specific features that do not translate well to the iOS API, mainly due to limitations of the Objective-C header and language differences between Kotlin and Swift. At this point, please consider whether using Android for scientific or prototyping purposes might be an easier long-term choice for you.

  1. Locate the zipped DynamicsMultiplatform.xframework in the provided SDK.

  2. Import the dynamic framework to your XCode project.

  3. Add the following permissions to your project's Info.plist:

    1. NSBluetoothAlwaysUsageDescription: Is required for accessing bluetooth APIs.

    2. NSMotionUsageDescription: Is required for pulling atmospheric pressure from the smartphone's sensor.

  4. Add the library KMP-NativeCoroutines v1.0.2 to your project as well. The library is used to map Kotlin Flows to AsyncSequence and Kotlin Coroutines Functions to Swift Async Functions.

  5. Be aware that many Kotlin specifics do not translate well to the iOS API (mainly due to the limitations of the Objective-C header and language differences between Kotlin and Swift/Objective-C), such as:

    1. Kotlin sealed classes and interfaces do not translate to Swift enums. Therefore, their advantages are lost and must be handled manually. However, if manual mapping to Swift enums is done, watch out for breaking changes when updating the SDK.

    2. Kotlin classes do not conform to Identifiable or Equatable by default. This may be important if such classes are used directly in SwiftUI.

    3. Some types, such as Date, or any classes wrapped in a Kotlin value class, are not translated to Swift by default but only into a “primitive” form.
